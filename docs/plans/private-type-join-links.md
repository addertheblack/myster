# Private Type Join Links and Invitation Redemption

## 1. Summary

Add a complete invitation-based private-type join flow: an administrator creates a time-limited
invitation link and separately shares a password; the recipient opens or pastes the `myster:` link,
finds the CID-pinned bootstrap through 3DNS, redeems the invitation over mutually authenticated
TLS, verifies its membership in the updated signed access-list chain, and only then imports the
type with the user's remembered enabled/disabled choice.

## 2. Non-goals

- Do not implement ordinary join requests, pending approval, an administrator inbox, denial state,
  polling, notification, or automatic retry. Those remain part of a future manual-approval or
  messaging milestone.
- Do not put invitation passwords in links generated by this version of Myster.
- Do not include an IP address, domain name, port, or signed onramp list in version 1 links. The
  bootstrap is located exclusively by its `ServerCid` through 3DNS.
- Do not implement firewall traversal, reverse connections, rendezvous, application-level proxying,
  or file relaying.
- Do not let invitations grant `ADMIN`, add writers, transfer an administrator signing key, or
  perform any access-list operation other than adding the authenticated caller as `MEMBER`.
- Do not synchronize invitation records between administrators. An invitation is redeemed only at
  the bootstrap node that created it.
- Do not import a type before the local authenticated server CID appears in the validated signed
  access-list chain.

## 3. Assumptions & open questions

- Owner-confirmed: the inviter chooses the invitation password. Myster does not generate it.
- Owner-confirmed: the invitation expiry is chosen when created from 24 hours, 7 days, or 30 days;
  7 days is selected by default.
- Owner-confirmed: links generated by this version omit the password. The URI grammar accepts an
  optional `code` parameter from another/future producer; when absent, the import dialog asks for
  the invitation code.
- Owner-confirmed: there is no manual approval path in this iteration. Failure imports nothing and
  does not create a pending request.
- Owner-confirmed: a version 1 link contains the bootstrap server CID but no address. 3DNS is the
  sole bootstrap-location mechanism.
- Owner-confirmed: successful import shows `Enable this type`, defaults it to checked on first use,
  and remembers the last choice for later imports.
- Owner-confirmed: native `myster:` activation and first-class desktop integration are required.
  Platform packages own scheme registration and removal; application startup never edits OS
  associations. Paste remains a fallback.
- The creating node has an exact 3DNS presence and accepts Myster TLS stream connections. A node
  that is offline, undiscoverable, or firewalled cannot redeem invitations in this milestone.
- Section number `126` is currently unused and becomes permanently reserved for type invitation
  redemption.
- No owner decision remains open.

## 4. Proposed design

### Link and creation flow

An administrator opens the existing Members tab for a locally administered custom type and chooses
`Create Invitation...`. The dialog asks for the password twice and offers 24 hours, 7 days, or 30
days, defaulting to 7 days. Creation stores a salted slow verifier and expiry locally, then displays
the invitation link with a `Copy Link` action. It never displays or copies a combined link/password
value. The user communicates the password separately.

Version 1 uses this canonical shape:

```text
myster://join-type/v1?type=<32-lowercase-hex>&bootstrap=<32-lowercase-hex>&invitation=<32-lowercase-hex>
```

`type` is the `MysterTypeCid`, `bootstrap` is the creating node's `ServerCid`, and `invitation` is
a random non-secret lookup id. Canonical generation orders parameters exactly as shown. Parsing is
order-independent, rejects duplicate known parameters, bounds the entire URI and every value,
requires the exact scheme/action/version, and ignores unknown parameters for forward compatibility.
The parser also accepts one optional `code=<percent-encoded-password>` parameter so another/future
producer can create a self-contained link. It is decoded once as UTF-8 and bounded to 256 Unicode
code points. This version's generator never emits `code`, its creator UI never offers to include
one, and string/log representations redact it.

### Recipient flow

`Join Private Network...` accepts a pasted link, while native URL activation opens the same dialog.
The dialog resolves `bootstrap` with `ThreeDnsLookup.resolve(...)`. Only `EXACT_VERIFIED` is usable;
closest, no-route, bounded, timeout, and cancellation outcomes do not contact or trust the closest
peer as the bootstrap.

The exact 3DNS result supplies both the bootstrap address and full RSA public key. All subsequent
TLS connections use that full key as the expected server identity. The client first fetches section
125 from the pinned bootstrap and validates that the returned access list derives the link's type.
This supplies the friendly type name before the user commits to joining.

Because generated links contain no password, the dialog requests it. On confirmation, the client
opens a pinned TLS connection and sends section 126. The server derives the requester solely from
`ConnectionContext.callerCid()`; the request never carries a claimed requester CID. A valid,
unexpired, unused invitation causes the bootstrap to synchronously append a signed
`AddMemberOp(callerCid, Role.MEMBER)` and save the access list before returning approval.

After `APPROVED` or `ALREADY_MEMBER`, the client fetches the complete access list again from the
same pinned server, validates it, and explicitly verifies that its own `ServerCid` is a member.
Only then does it persist/register the type. The remembered `Enable this type` checkbox determines
the initial enabled state. Any failure leaves both the type registry and access-list storage
unchanged.

### Invitation security and lifecycle

Invitation ids are 128 random bits. Their canonical URI representation is exactly 32 lowercase
hexadecimal digits; protocol and persisted representations use the raw 16 bytes. Passwords are
case-sensitive, must be non-empty, are bounded before KDF work, are never logged, and are not
stored. Persist a random 128-bit salt, PBKDF2-HMAC-SHA256 parameters, a 256-bit verifier,
creation/expiry timestamps, type CID, invitation id, and optional consumed-by CID. Use a
constant-time verifier comparison.
Production PBKDF2 parameters are stored per record so they can evolve; tests inject deliberately
cheap parameters.

Expiry is enforced by the bootstrap's clock. Expired records are lazily discarded during store
load, listing/creation, and redemption; no timer is required. Wrong, expired, missing, and consumed
by another identity all produce the same `INVITATION_NOT_ACCEPTED` wire status and user message.
This avoids exposing invitation state. A consumed invitation retried by the identity already added
returns `ALREADY_MEMBER`, making response loss safe. It cannot add a second identity.

KDF verification is concurrency-bounded and failed attempts are throttled by invitation id,
authenticated caller CID, and remote address. Throttling must not globally invalidate an invitation
after a small number of failures because that would permit trivial denial of service. Requests and
responses use bounded MessagePak frames, and malformed data closes the section without mutation.

### Membership mutation and persistence

Introduce one membership service as the only new path for invitation redemption, direct Members-tab
addition/removal, and persistence. It serializes mutation per type, reloads the cached list under
that ownership, verifies the signing key is still a writer, appends once, and atomically saves.
This prevents the new server thread from racing the existing EDT member editor.

Invitation records are local operational state under the private data path, not signed shared type
metadata. Store one versioned MessagePak file per administered type beneath `TypeInvitations`, use
bounded decoding and temp-file plus atomic-replace persistence, and tolerate a corrupt file by
quarantining/ignoring it rather than weakening access-list validation.

### Native URL activation

All activation paths feed a single bounded URI dispatcher and always show the confirmation dialog;
opening a link never redeems it automatically. Initial process arguments and arguments forwarded by
`ApplicationContext` are retained until GUI services are ready. Normal relaunch without a URI keeps
the existing bring-window-to-front behavior.

On macOS, the packaged app declares `myster` in `CFBundleURLTypes`; Launch Services discovers the
bundle declaration and delivers activations through `Desktop.setOpenURIHandler(...)`. On Windows,
the jpackage WiX installer owns the `Software\\Classes\\myster` URL-protocol keys and removes them
on uninstall. On Linux, the DEB installs a normal XDG application entry containing `%u` and
`MimeType=x-scheme-handler/myster;`; package install/removal owns the declaration and refreshes the
desktop database. Myster appears in the Linux application launcher even apart from link handling.
Raw `java`, test, and `-s` launches never alter OS registration. A missing/broken package
association still leaves paste/command-line import available.

## 5. Architecture connections

The invitation creator uses the existing access-list writer key but creates only local ephemeral
authorization state. A recipient link enters through native activation, command-line forwarding, or
the Type Manager toolbar, and all three converge on one parser/dialog. `ThreeDnsLookup` transforms
the bootstrap CID into an exact verified address/key pair. That key pins TLS while section 125
provides signed type metadata and section 126 redeems the invitation. The server uses TLS caller
identity and the local writer key to append normal signed membership; there is no parallel
membership database. The recipient distrusts the success status until the new signed chain proves
membership, then calls the type registry's import path with the user's enabled choice.

### Version 1 URI contract

- Scheme: `myster` (case-insensitive on parse, canonical lowercase on output).
- Authority/action: `join-type`.
- Path: `/v1` exactly.
- Required query parameters: one each of `type`, `bootstrap`, and `invitation`.
- `type`, `bootstrap`, and `invitation`: exactly 32 lowercase hexadecimal characters decoding to
  exactly 16 bytes. Decode the two CIDs through their domain types.
- Optional query parameter: at most one `code`, UTF-8 percent-encoded and bounded to 256 decoded
  Unicode code points. Current generation omits it and all diagnostic/string forms redact it.
- No address, port, fragment, user-info, or additional path segment is allowed.
- Unknown query parameters are ignored; duplicate known parameters (including `code`) are rejected.
- Maximum complete URI length: 4 KiB.

### Section 126 wire contract

The existing connection-section acknowledgement happens before the request. Both request and
response are length-prefixed MessagePak frames read with a new bounded input helper.

Request schema version 1:

```text
/schemaVersion  int     1
/type           binary  16-byte MysterType CID
/invitation     binary  16-byte invitation id
/code           string  inviter-chosen password, bounded to 256 characters
```

Response schema version 1:

```text
/schemaVersion  int     1
/status         string  serialized TypeJoinStatus identifier
```

Initial canonical statuses are `APPROVED`, `ALREADY_MEMBER`, `INVITATION_NOT_ACCEPTED`,
`TYPE_NOT_FOUND`, `NOT_AUTHORIZER`, and `ERROR`. Unknown future status identifiers deserialize to a
non-canonical `TypeJoinStatus`; this client treats them as an unsupported/generic failure while
retaining forward-compatible decoding. Frames are capped at 4 KiB. Error responses carry no raw
exception text or invitation-state detail.

## 6. Key decisions & edge cases

- **CID-only links are deliberate.** They are smaller, stable across address changes, avoid a
  misleading or private endpoint, and give version 1 one verified discovery route. A future version
  may add address hints without changing the action or type identity.
- **3DNS exact proof is mandatory.** A closest verified peer is useful routing evidence but is not
  the invitation bootstrap. Never send a password to it.
- **TLS identity and invitation authority are separate.** TLS proves which requester is joining;
  the password authorizes adding that requester. The payload cannot override TLS identity.
- **The signed chain is final proof.** A successful status alone never authorizes local import.
- **No manual fallback.** Missing/wrong/expired invitations do not create requests for later
  approval. The user may correct the password or ask the inviter for a new invitation and explicitly
  try again.
- **Ambiguous invitation failures are intentional.** The UI says the code may be incorrect or
  expired. 3DNS/connection failure separately says the bootstrap could not be found and may be
  offline.
- **Already-member retries are safe.** If the same caller was added before a response was lost, it
  can fetch and import. If a different caller presents the consumed invitation, it is not accepted.
- **Expiry boundaries use the server clock.** An invitation is invalid when `now >= expiresAt`.
- **Password confirmation is local only.** The creation dialog requires matching entries before
  performing KDF work. It does not impose composition rules, but warns that short/common passwords
  are easier to guess.
- **Existing type handling:** if the type is already registered and the local CID is a member, show
  `Already joined`; optionally apply the enable checkbox without duplicating or downgrading the
  stored chain. Never replace a built-in type or discard a local administrator key.
- **Public types:** this flow is intended for restrictive custom types. If fetched policy is already
  public, the dialog explains that no invitation is required and uses the existing import path
  instead of redeeming a password.
- **Cancellation:** closing the dialog cancels active 3DNS and network promises and prevents late UI
  or import mutation. Server-side redemption already committed before disconnect remains committed;
  a later retry resolves through `ALREADY_MEMBER`.
- **Unknown URL/wire versions:** reject safely and tell the user this Myster version cannot open the
  invitation.
- **Server unavailable:** do not retry automatically. Preserve the entered link in the dialog so
  the user may choose to try again explicitly.
- **No password leakage:** never log URI password fields, protocol code, verifier input, clipboard
  contents, or exception messages that embed them.

## 7. Acceptance criteria

- [ ] An administrator can create an invitation using a confirmed chosen password and select 24
      hours, 7 days, or 30 days, with 7 days initially selected.
- [ ] The generated canonical link contains type CID, bootstrap CID, and invitation id, but no
      address or password.
- [ ] Opening a registered `myster:` link or pasting it into `Join Private Network...` reaches the
      same confirmation dialog and never redeems without explicit user confirmation.
- [ ] The dialog asks for a password when the parsed link does not contain one.
- [ ] A valid externally supplied optional `code` parameter can prefill the password without ever
      appearing in generated links, logs, or diagnostic strings.
- [ ] Bootstrap discovery accepts only an exact verified 3DNS result and pins subsequent TLS to its
      public key.
- [ ] A valid unexpired invitation synchronously adds the TLS-authenticated caller as `MEMBER` and
      consumes the invitation once.
- [ ] The client imports only after a newly fetched, valid signed chain contains its local CID.
- [ ] The import enable checkbox defaults checked, remembers the last selection, and imports a
      successfully joined type enabled or disabled accordingly.
- [ ] Wrong, expired, missing, or other-identity-consumed invitation credentials import nothing and
      reveal no specific invitation state.
- [ ] A response lost after membership append can be retried by the same identity without another
      `AddMemberOp`.
- [ ] A different identity cannot reuse a consumed invitation.
- [ ] There is no pending-request persistence, approval UI, polling, or automatic retry.
- [ ] Expired invitation records are removed lazily and never accepted.
- [ ] Concurrent direct member edits and invitation redemptions cannot fork or overwrite the local
      access-list file.
- [ ] Windows, macOS, and Linux packaged GUI installations declaratively register `myster:`;
      Windows/Linux uninstall removes the package-owned association and the macOS declaration lives
      only in the application bundle. A second launch forwards the complete URI to the running
      instance; raw development/server launches do not alter OS registration.
- [ ] The Linux DEB installs a standards-compliant, menu-visible Myster desktop entry with its icon,
      application category, `%u` URL delivery, and `x-scheme-handler/myster` capability.
- [ ] Malformed/oversized links and frames fail without excessive allocation, KDF work, logging a
      password, or mutating type/access state.

## 9. Step-by-step implementation

1. **Implement and freeze the URI value contract.**
   - Build `TypeJoinUri` around `java.net.URI`, not string splitting.
   - Enforce the exact version 1 grammar and 4 KiB total bound from section 5.
   - Generate 16-byte invitation ids with `SecureRandom` and encode their canonical URI form as
     exactly 32 lowercase hexadecimal digits.
   - Parse one optional UTF-8 percent-encoded `code` parameter, reject malformed encoding or more
     than 256 decoded Unicode code points, and expose it only as secret-bearing state to the join
     dialog. Never include it from the version 1 invitation creator or in `toString()`/logs.
   - Add exhaustive parser round-trip and rejection tests before UI or networking uses it.

2. **Add bounded MessagePak input.**
   - Implement `MysterDataInputStream.readMessagePack(int maxBytes)` by reading the signed length,
     rejecting negative or over-limit values before allocation, reading exactly that many bytes,
     and delegating to `MessagePak.fromBytes`.
   - Use the 4 KiB overload for both section 126 request and response. Do not silently change every
     existing protocol in this feature.

3. **Implement password verification and invitation persistence.**
   - `InvitationLifetime` contains `TWENTY_FOUR_HOURS`, `SEVEN_DAYS`, and `THIRTY_DAYS`; UI labels are
     `24 hours`, `7 days`, and `30 days`, and the dialog initially selects `SEVEN_DAYS`.
   - `InvitationPasswordVerifier` uses `PBKDF2WithHmacSHA256`, 128-bit random salt, 256-bit output,
     and stores algorithm/version/iteration parameters with each record. Keep production cost in a
     named policy constant and inject a cheap test policy. Clear `PBEKeySpec` and temporary mutable
     buffers where possible.
   - Reject empty codes and codes over 256 characters before KDF work; require matching creation
     fields in the UI. Do not trim or change case silently.
   - Store files at `{PrivateDataPath}/TypeInvitations/{typeHex}.msgpack`. Frame a format version and
     numbered invitation records. Bound record count and file size; discard expired records while
     loading. Persist with a sibling temp file and `Files.move(..., ATOMIC_MOVE, REPLACE_EXISTING)`,
     with a safe same-filesystem replacement fallback where atomic move is unsupported.
   - On corruption, move the bad file aside with a timestamped `.corrupt` suffix when possible,
     start with no invitations for that type, and log without record secrets.

4. **Centralize membership mutation.**
   - Add per-type locking in `TypeMembershipService` rather than synchronizing unrelated types on a
     single global monitor.
   - Under the type lock: load the access list and local writer key, confirm the key remains in
     `state.getWriters()`, return already-member without appending, otherwise append
     `AddMemberOp(cid, MEMBER)` and save before success.
   - Add equivalent remove-member entry point used by `TypeEditorPanel`; keep direct picker behavior
     unchanged except for routing append/save through this service.
   - Make invitation consumption and member append crash-idempotent: validate record, perform member
     mutation, then persist consumed-by. On retry, an already-member caller matching the intended
     redemption completes consumption and returns `ALREADY_MEMBER`.

5. **Implement invitation lifecycle and abuse bounds.**
   - Creation accepts type, password chars, chosen lifetime, and `Clock`; it verifies the local
     writer key before spending KDF work or storing a record.
   - Redemption accepts type, id, password, authenticated caller CID, and remote address.
   - Check format/existence/expiry and attempt limits before KDF; perform constant-time verification;
     call `TypeMembershipService`; consume only for the successful/already-member caller.
   - Use a small semaphore to bound concurrent PBKDF verification. Maintain bounded expiring
     backoff entries keyed by `(invitationId, callerCid, remoteAddress)`; all rejections map to the
     same public status. Prune limiter state opportunistically.

6. **Add section 126 and pinned stream support.**
   - Reserve `TypeJoinServer.NUMBER = 126` and register it beside section 125.
   - Reject `context.callerCid().isEmpty()` before decoding a password-bearing request.
   - Decode only schema 1, exact CID/id lengths, and bounded code; never read a caller CID from the
     payload. Map internal results to the six canonical `TypeJoinStatus` values and never serialize
     exception text.
   - Add `MysterSocketFactory.makeStreamConnection(address, expectedServerPublicKey)` delegating to
     the existing `TLSSocket` expected-key path.
   - Extract an `AccessListGetClient.fetchAccessList(MysterSocket, MysterType)` full-chain overload;
     the address overload opens a connection and delegates. Do not use the currently incomplete
     incremental-suffix path for this workflow.
   - `TypeJoinClient` writes/reads section 126 on a caller-owned pinned socket and, after approved or
     already-member, fetches a fresh full chain through section 125 on that same socket.

7. **Build the cancellable join coordinator.**
   - Construct production `ThreeDnsPeerClient(protocol.getDatagram())` and
     `ThreeDnsLookup(tracker, peerClient)` in `Myster`.
   - `prepare(uri)` resolves the bootstrap CID and accepts only `result.exactPeer()`. Open pinned TLS
     to that verified peer and fetch the full access list. Reject missing/mismatched/invalid chains.
     Return a preview containing friendly metadata and the verified bootstrap peer without
     modifying persistent type state.
   - `redeem(preview, code, enable)` runs the blocking pinned stream work on a virtual thread,
     handles only `APPROVED`/`ALREADY_MEMBER` as success candidates, validates the returned chain,
     verifies `state.isMember(localServerCid)`, then imports.
   - Compose with `PromiseFuture`/`mapAsyncInline` and explicit invokers according to the concurrency
     conventions. Cancellation owns 3DNS and active network tasks and makes later outcomes moot.
   - Translate failures at the UI boundary: non-exact 3DNS/connect errors become bootstrap-not-found;
     invitation rejection becomes incorrect-or-expired; unsupported versions/statuses become
     client-version errors; validation failures become invalid-network errors.

8. **Extend type import without premature enablement.**
